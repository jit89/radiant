Every row ran through `proof_exec` under the proof sandbox, as the host runs a
proof:
- the command was `cd <checkout> && <proof>`;
- `CARGO_HOME` was the walk's deps folder (read-only), except the vendored row;
- `TMPDIR` was private, with no network unless a row says loopback;
- each row had a fresh git copy of `fixture/notes-sqlite/` with one plant

The full recipe is exactly the one RUST-AXUM-SQLX.md publishes. The harness
unsets `DATABASE_URL`, `SQLX_*`, `CLANG_MODULE_CACHE_PATH`, `SDKROOT`, `PG*`
and the core item's list before every run, and each log opens with what the
proof saw (`env:` lines):
- `CARGO_HOME`;
- `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk`, set inside
  the proof by the command-line tools' shims, as it would be in a real walk.

A row's own `export` (such as `SQLX_OFFLINE=true`) comes after that line.

`fixture/run-plants.sh all` reruns everything. The trap (`notes-trap`) counts
only on the line after libtest's `panicked at` line. Per-case results are
libtest's `test <name> ... ok|FAILED` line. Times are cargo's own. The plants
are generated by `fixture/plants-gen.py`.

## The fixture

- **`notes-sqlite/`:**
  - the planned API: `create_note`, `get_note`, `delete_note`, five Tier 2
    helpers, the `NoteRepo` seam, the handlers, `router` (the routes, no
    layers) and `app` (`router` plus `CatchPanicLayer`);
  - the stub: the route wiring is real and every handler and function body
    traps, so a request reaches a trap inside a request;
  - `impl/lib.rs`: the correct implementation, using the unchecked sqlx API.
- **Oracles:** `g1` (the repository functions), `g2` (the routes through
  `oneshot` on `router`, with error cases pinning the body's error code) and
  `g3` (SQLite semantics). Every case is
  `#[sqlx::test(migrations = "./migrations")]`. Each file opens with
  `#![forbid(unused_must_use, unreachable_code)]`.

## Step 2b: Postgres, stopped

`fixture/postgres-probe.sh` probes Postgres 18.6 (Homebrew `postgresql@18`,
keg-only) through `proof_exec`, with `TMPDIR` placed exactly where
`run-goal.sh` puts it. Its transcript is `fixture/postgres-probe.txt`:

| Probe | Result |
|---|---|
| the socket path `$TMPDIR/.s.PGSQL.5432` (NUL included) for goal ids of 2 / 12 / 23 characters | 86 / 96 / 107 bytes; the cap is 104, so run-goal.sh's `TMPDIR` fits goal ids up to 20 characters with this `$HOME` |
| `initdb` inside the sandbox | `could not look up effective user ID 501: user does not exist` |
| `initdb` outside, the server inside, with `shared_memory_type=mmap` and `dynamic_shared_memory_type=mmap` | `FATAL: shmat(...) failed: Operation not permitted`, then `shmctl(…) failed`; `deny ipc-sysv-shm`. Postgres always attaches a small System V segment |

- **The `initdb` cause, confirmed by experiment**
  (`fixture/postgres-initdb-cause.sh`, transcript
  `postgres-initdb-cause.txt`). Under the generated profile, `initdb` fails on
  the user lookup. With the same profile plus only `(allow mach-lookup
  (global-name "com.apple.system.opendirectoryd.libinfo"))`, a diagnostic
  never proposed for the profile, it gets past the lookup and fails creating
  shared memory instead. The first probe's console also showed that denial.
  The kept probe transcript's listing for those windows is empty, which is
  unexplained (cargo's identical denial is logged in every 2b run).
- **Sandboxed postgres leaves System V segments behind.** The two runs
  failed at different steps:
  - in the first probe, the server created a segment and was refused the
    attach (`shmat(...) failed`), then the cleanup (`shmctl … failed`);
  - in the first diagnostic run, `initdb`'s bootstrap reported `could not
    create shared memory segment`, yet a 56-byte segment was left by an
    earlier step of the same `initdb`.

  Two were found and removed: id 589824 (the probe's server, pid 5932) and id
  983040 (the diagnostic's `initdb`, pid 44849). Each was 56 bytes with
  nothing attached. Both scripts now remove what a run leaves.
- **After the kept runs,** the user owns no System V segments (`ipcs -m`).

The signed plan forbids allowing global System V IPC, so the Postgres half
stopped. The user chose to finish SQLite here and open FUTURE-WORK item 35.
No server was left running.

## Tier 1 rows (run 2)

The recipe is the full one unless a row says otherwise: the core RUST.md rules
plus this item's checks `C_layer`, `C_pool` and `C_macro`, and the guard
`X_db` (`export DATABASE_URL=`).

`row_case` scores a plant placed beside trapping siblings. The minus run must
be a Tier 1 pass, and then one of two grounds must hold under it:
- **per-case:** the planted case is `ok` on the stub;
- **tamper:** the tree moved.

A rule is kept when the full run is not a Tier 1 pass. On the tamper ground,
the full run must also leave the tree unchanged.

| Row | Plant | Minus | Full | Verdict |
|---|---|---|---|---|
| clean g1, g2, g3 | none | — | stub rc 101 + trap, impl rc 0, tree unchanged | (a)(b)(c) hold |
| a1 | a `500` error-path case calling `app()` (with `CatchPanicLayer`) | Tier 1 pass, **the planted case `ok` on the stub** (the trap became a 500) | rc 1, no trap | **kept**: `C_layer` (`CatchPanicLayer` or a call to `app(` in an oracle) |
| a1, corrected form | error cases on `router()` pinning the body's error code (`g2` clean) | — | (a)(b)(c) hold | the written form |

| a2 | the same under loopback | — | implementation rc 0 (case ok); stub without a timeout: rc 101, no hang | a timeout is not needed |

### Checked macros (Q2) and the environment

The plant is `get_note` written with `sqlx::query_as!`. A matching `.sqlx/` was
prepared outside any proof, the way an Architect with a database would: an
online build against a scratch database holding the migrations, with
`SQLX_OFFLINE_DIR` set. The directory must exist first: sqlx writes into it,
and refuses a missing one. The cache is keyed by the lockfile, the plant and
the migrations.

| Run | Result |
|---|---|
| a diagnostic grep outside the proof for `(^\|[^A-Za-z0-9_])query(_file)?(_as\|_scalar)?(_unchecked)?!` | matches the plant |
| minus `C_macro`, `DATABASE_URL=` exported empty, `.sqlx/` present | **rc 0**: the empty value selects the cache, and the macro code builds and passes |
| the same plus `SQLX_OFFLINE=true` | rc 0 |
| minus `C_macro`, no `.sqlx/` | rc 101, compile error (`set DATABASE_URL … or run cargo sqlx prepare`) |
| full | rc 1: the check |

So `C_macro` changes a verdict and is **kept**. The regex also matches the
`_unchecked` forms, which need a database or `.sqlx/` at build time just the
same.

A parent folder's `.env` with `DATABASE_URL=sqlite:///nonexistent-dir/x.db`
(sqlx reads every ancestor's `.env`), cold builds:

| Code | `unset` only | `export DATABASE_URL=` |
|---|---|---|
| the clean oracle (unchecked API) | rc 0 | rc 0 |
| the macro plant with its `.sqlx/`, `C_macro` removed | **rc 101, compile error** (`unable to open database file`: the build went online to the `.env`'s URL) | rc 0 (the cache) |

`X_db` is a **guard, not a kept rule**. Under the full recipe it changes no
verdict: the clean oracle passes either way, and `C_macro` rejects macro code.
It stays in the recipe because the plan put it there, it costs nothing, and a
stray `.env` must not matter if the macro ban is ever lifted.

## Dropped

- **`CLANG_MODULE_CACHE_PATH`:** with or without it, the C build has the same
  denials and the same result.
- **A timeout around a listener read:** nothing hung.
- **`SQLX_OFFLINE=true`:** the empty exported `DATABASE_URL` already selects the
  cache. It stays the plan's fallback, unused.

## Departures from the plan

- **Postgres** stopped at step 2b, so its plants and Tier 2 rows were not built
  (FUTURE-WORK item 35).
- **`run-plants.sh`** was written fresh with the core item's functions, not
  extended in place, because the fixtures differ too much for one file.
- **Rows added:**
  - s4c, the warm, test-unchanged staleness, after s4b showed that a test
    change re-expands the macro;
  - a3b (extractor rejection) after the Opus round-1 review.
- **The trap reader** was measured under the sandbox for `oneshot` and a
  spawned server on the test's own runtime. The `CatchPanicLayer` and
  multi-thread shapes come from the unsandboxed prototype.

## Runs

- **Run 1** found two harness defects:
  - `SQLX_OFFLINE_DIR` must exist before sqlx writes into it;
  - s4b could not show staleness, which s4c then measured.
- **The Opus round-1 review** found that the full recipe still carried the
  dropped `CLANG_MODULE_CACHE_PATH`. That was removed, and so:
  - every row was rerun as **run 2** (the evidence above), with the stricter
    `row_case` scoring, the keyed `.sqlx` cache, the widened macro regex and
    the narrowed pool pattern;
  - run 2's verdicts match run 1's, plus a3b.
- **Run 3,** after the Opus round-2 review: the left-anchored macro regex,
  `row_case` requiring an unchanged tree on the tamper ground, the reference
  row without the clang redirect, and s4a printing its reason. `prep_sqlx` now
  applies every migration, but run 3 reused run 2's cache (same key, one
  migration), so that code path did not run. Every verdict is identical to run 2's, and s4a now
  shows `UNIQUE constraint failed: _sqlx_migrations.version`. The timings
  above are run 2's.
