## Findings

### F1 (High, house): `caffeinate -i` doesn't hold a Mac that is already in dark wake
- **Location:** `scripts/lib/cache.sh:60-63` (`cw_keep_awake`: `caffeinate -i -w $$`), from FUTURE-WORK item 23.
- **Evidence:**
  - At 05:39:24 the first walk stopped (wave-stop). Its assertion died ("ClientDied PreventUserIdleSystemSleep …
    01:09:12", "System: No Assertions"), and `pmset` entered "Idle Sleep" five seconds later. `pmset -g` shows
    `sleep 1`, one minute on AC.
  - From then on the machine ran only in **DarkWake** slices of about 5 minutes ("DarkWake from Deep Idle …", then
    "Entering Sleep state due to 'Maintenance Sleep'"). That held even while `run-goals.sh` and `run-goal.sh` each
    held their `-i` assertion.
  - A PreventUserIdleSystemSleep assertion keeps a fully awake system from idling to sleep. It doesn't stop a
    maintenance sleep out of dark wake. So the whole rerun, 06:23–11:46, ran in bursts.
  - The implementers' transcripts show the same thing from inside: `api_error` "Connection lost while your computer
    was asleep" (`StreamSuspended`) and "Request timed out" after 15–17 minutes. Each one falls in a sleep window.
- **Why it matters:** about half the walk's wall time. FUTURE-WORK item 23 fixed idle sleep on battery from a fully
  awake machine; this is the other case.
- **Fix:**
  - `caffeinate -i -s -w $$`. `-s` (PreventSystemSleep) is honoured on AC, including in dark wake. A closed lid
    still sleeps unless the Mac is in clamshell mode with an external display.
  - The house test that already finds the assertion by the helper's pid also checks that its type is
    PreventSystemSleep.
- **Out of scope:** keeping the Mac awake between a wave-stop and the Architect's rerun. That is the owner's choice;
  the Architect can hold `caffeinate -is` around `walk-watch.sh` if wanted.

### F2 (Medium, prompt): step 9 asks for the full suite after the proof, and that duplicates the proof
- **Location:** `claude-implement.sh:735-736`: "9. Run the goal's PROOF command, then the full test suite if one
  exists, and report the real result."
- **Evidence:**
  - g38 r1 committed its fix 4 minutes into the pass. It then ran `cargo test --workspace --no-fail-fast` (16
    minutes) on top of the proof, which already runs every test target. The run went past the Bash tool's 10-minute
    limit, so it backgrounded it and polled with `sleep 20; tail` for another 10 minutes. Its END record: "a single
    foreground `cargo test --workspace --no-fail-fast` exceeded the sandbox's 10-minute limit, so the suite was run
    as those parts".
  - Six END records in M1b ran `--no-fail-fast` suites beside the proof.
- **The conflict:** the fix handoff says "Do not redo passing tests" (`run-goal.sh:1842`), while step 9 and the resume
  prompt ("Run the goal's proof before claiming DONE") ask for everything again.
- **Fix (hunk 1):**
  - Step 9 becomes: "Run the goal's PROOF command and report its real result. The proof is the suite the host runs
    after you; run more only when it leaves code you changed untested, and say what."
  - The resume prompt adds: "While fixing, run the oracle and the tests of the code you touched; run the proof once,
    at the end."

### F3 (Medium, prompt plus a target key): every implementer rediscovers the same eight host-blocked tests
- **Evidence:**
  - 22 of the 26 END records spend lines on the same tests: g9's two socket-helper tests, g10's socket child, g12's
    four `sysctl kern.*vnodes` readers, and g14's performance-core reader. They name them, explain them and
    re-count them; g34 appended a correction because it miscounted ("seven" became "eight").
  - Their sandbox denies unix-socket `bind(2)` under `$TMPDIR` and these `sysctl` reads. The host proof runs all
    eight green.
  - The `--no-fail-fast` passes and the hand-made proof segments are how each pass works around them. g37 r1 and
    g38 r1 both `sed` the `--test g9-bulk-sys …` names out of the proof and run it as 13 segments.
- **Fix:**
  - **(a) The target key:** an optional top-level key in GOALS.md, `implementer_sandbox_skips:` (a list of
    `test-binary::test-name`). The handoff prints it under the proof line: "These fail only in your sandbox: run the
    proof with them skipped (`-- --skip <name>`), name them in the END record, and the host runs them." Paladin sets
    the eight.
  - **(b) Investigate first:** whether Claude Code's sandbox settings (`sandbox.network.allowUnixSockets` for paths
    under `$TMPDIR`) let the socket tests run outright. That would leave only the four `sysctl` readers and g14.
- **The cost today:** about 15–25 lines of every END record, plus a proof the implementer has to cut up by hand.

### F4 (Low, house): the Bash tool's 10-minute cap pushes long proofs into background polling
- **Evidence:** g38 r1's backgrounded suite and `sleep 20` polling (10.3 minutes in a single call); g36 and g38 split
  the proof into segments.
- **Fix:** `claude-implement.sh` sets `BASH_MAX_TIMEOUT_MS` (Claude Code's cap for one Bash call) to the proof's own
  bound, `PROOF_SECS`, or 30 minutes, for the implementer's environment. The prompt then needs no word about it.
